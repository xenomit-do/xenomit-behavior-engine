# General behavior rules

General behaviors are global policies evaluated beside the active objective module. Their settings persist in the top-level `behaviors` field in `modules.json`, on the separate `__behaviors` settings page, independent of `modules.<module-id>`. Each rule has an `enabled` flag, a `tick_stopped` flag, and an `options` object. At launch the controller injects these settings into the module config after merging that module's settings, so a module payload cannot replace global rule settings. Lower numeric registry priority runs first. A takeover suspends the objective module for that tick; lower-priority rules pause during a takeover so discarded actions cannot consume cooldowns. Combat item selectors may supplement a defense takeover. Built-in module health safety takes precedence over defense and travel rules.

Periodic refresh is a native Base behavior with direct `enabled` and `interval_minutes` settings, rather than the upstream `options` format. Its timer runs while an objective is active. Once overdue, it requests permission through `BehaviorModule::interruption_status`; a deferred request keeps the module running normally. Gates defer until the hero leaves the gate, and durable task sequences defer until completion. The controller checks permission before ticking the objective again, so it refreshes before another gate starts. Completed sequences refresh without automatically replaying. Existing emergency recovery refresh actions retain their separate immediate semantics.

This is a behavior port, not a claim of feature parity with DarkBot. The upstream plugins have access to richer game APIs, events, UI, client internals and profile/config services than this controller exposes. Rules below are only effective when the described snapshot facts or host services are actually supplied. Unknown facts should be treated as unknown, not as a positive match.

## Condition JSON

`condition` accepts a JSON object whose entries are all required. Supported keys are `hp_below` and `shield_below` (fractional ratios), `attacking` (boolean), `map` (numeric map id), `map_time_ms`, `elapsed_ms`, `deaths`, `target_name` (case-insensitive substring), `field` (hero field equality map), `key_empty` (booty key name), `npc_kills` and `resources` (name-to-minimum maps), and `time` (`hour` plus `minute`, accepted for a five-minute window). An empty object matches; a non-object or unrecognized key does not. Time depends on the supplied hero-local `localHour` and `localMinute` fields.

Profile changer `conditions` is an array of these objects; `match` is `all` by default or `any`. `custom_events` entries have `condition`, `item`, optional `minimum`, `select`, `activate`, and `cooldown_ms`. Anti-train `items` uses the same event shape. `auto_cloak.condition` is one such condition.

## Host integration and required data

The rules engine emits `GameCommand`s for game calls and `HostAction`s for controller operations. The controller queues disconnect, close, refresh, profile-switch, and player-tag actions; it handles `SelectTarget` by invoking the game ship manager. Urgent-quest acceptance and calendar claiming run through the named `game.urgent_quest` and `backpage.calendar` services. Enabling calendar claiming, or enabling urgent detection with take_quest=true, requires its service to be registered or startup rejects the configuration. Urgent profile switching can run without the acceptance service. Availability of those services and game observations varies by backend and session. The engine cannot manufacture observations that a client backend does not capture.

The common snapshot contract uses a player entity, item inventory in `navigation.hero.items`, `navigation.map_id`, `navigation.portals` and the star-system catalog, `navigation.group.members`, and map safe places. Dynamic entity fields consumed by rules include: `isEnemy`, `isBlacklisted`, `isAlly`, `isPet`, `isAttacking`, `isAttacked`, `attackingHero`, `attackingTargetId`, `localTargetId`/`lockedTargetId`, `lastDestroyerId`/`lastDestroyerName`, `effects`, `isInvisible`, `isPvp`, `isGG`, `speed`, `clanId`, `preferredAmmo`, `preferredFormation`, and `formation`. Hero-only fields include `bootyKeys`, `captcha`, `credits`, `npcKills`, `resourcesCollected`, `localHour`, `localMinute`, urgent-quest/calendar flags, `clientMemoryMb`, and `pingMs`. Backends may omit fields; these rules generally skip an action when required data is absent.

## Verified ID corrections

Compared hard-coded candidates against the checked-in DarkBot `SelectableItem.java` and local game resources. The rule implementation now uses canonical IDs for these previously mismatched values:

* Abilities: Tempest backup (`ability_tempest_volt-backup`), Berserker revenge/berserk (`ability_berserker_rvg`/`ability_berserker_bsk`), and Solaris Incinerate (`ability_solaris_inc`).
* Formations: Veteran `drone_formation_f-3d-vt`, Wheel `f-3d-wl`, Crab `f-10-cr`, Diamond `f-07-di`, Barrage `f-12-ba`, Star `f-04-st`, Pincer `f-05-pi`, Double Arrow `f-06-da`, and Drill `f-3d-dr`; standard formation uses ID `default`.
* Ammo: SP-100X is `ammunition_specialammo_sp-100x`; rocket-launcher BDR-1212 is `ammunition_rocketlauncher_bdr1212`.

`rule_support.rs` contains canonical ability candidate groups and the full supported-ability set corresponding to the audited DMPlugin revision. The active rule has not yet been wired to all groups, so that list documents verified extension points rather than complete behavior coverage.

## Upstream scope exclusions

The DefaultPlugin checkout also contains `PalladiumModule` (an objective module), `UserAgentUpdater` (a task), sample code and verifier/authenticity checks. They are not general behaviors and are not represented by these rules. DmPlugin also contains objective modules, tasks, GUI/MCP integrations, backpage utilities and other plugin features that are outside its `Behavior` implementations. This document covers the behavior-oriented port represented in `rules.rs` and records the service/data boundary instead of asserting full plugin parity.
